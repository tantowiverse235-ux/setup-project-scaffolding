# Requirements Document

## Introduction

Travel Planner SaaS is a web application built with Next.js (App Router, TypeScript) that enables solo travelers and group trip organizers to plan itineraries, manage budgets, split expenses, and discover destinations — with a particular focus on Indonesian travel. The system supports real-time collaborative trip editing, day-by-day drag-and-drop itinerary building, IDR-denominated expense tracking with automatic settlement calculations, and a curated place recommendation module.

---

## Glossary

- **System**: The Travel Planner SaaS web application as a whole.
- **Auth_Service**: The module responsible for user authentication, session management, and OAuth integration.
- **User**: A registered account holder who can create and join trips.
- **Profile_Service**: The module that manages user profile data.
- **Trip**: A planned travel event with a destination, date range, and type (Solo or Group).
- **Trip_Service**: The module responsible for creating, reading, updating, and deleting trips.
- **TripMember**: A User who has been granted access to a Trip with a specific role.
- **Collaboration_Service**: The module that manages invitations, roles, and membership within a Trip.
- **Role**: A permission level assigned to a TripMember — one of ``Owner``, ``Editor``, or ``Viewer``.
- **Itinerary**: The ordered collection of ItineraryItems associated with a Trip, organized by day.
- **ItineraryItem**: A single activity or place entry within a day of a Trip's Itinerary.
- **Itinerary_Service**: The module responsible for managing ItineraryItems, including creation, reordering, and deletion.
- **Expense**: A financial transaction logged against a Trip, denominated in IDR.
- **ExpenseSplit**: A record defining which TripMembers share an Expense and their respective shares.
- **Budget_Service**: The module responsible for expense logging, split calculation, and settlement generation.
- **Settlement**: A derived payment instruction indicating that one TripMember owes another TripMember a net amount.
- **Recommendation_Service**: The module that provides curated place and destination suggestions for Indonesian travel.
- **Place**: A point of interest (destination, attraction, restaurant, etc.) surfaced by the Recommendation_Service.
- **Dashboard**: The main UI view for a Trip, showing itinerary, budget summary, and member status.
- **IDR**: Indonesian Rupiah, the currency unit used for all monetary values in this system.
- **Drag-and-Drop**: The user interaction that allows reordering ItineraryItems within a day by dragging them.
- **Invitation_Link**: A unique URL generated by the Collaboration_Service that grants access to a Trip.

### Requirement 1: User Registration and Email/Password Authentication

**User Story:** As a new visitor, I want to register with my email and password, so that I can create a personal account and access the application.

#### Acceptance Criteria

1. WHEN a registration request is submitted with a valid email and a password between 8 and 128 characters, THE Auth_Service SHALL create a new User account.
2. WHEN a registration request is submitted, THE Auth_Service SHALL validate that the email address conforms to the RFC 5322 format before creating the account.
3. WHEN a registration request is submitted with an email address already associated with an existing User, THE Auth_Service SHALL return an error indicating the email is already in use without creating a new account.
4. WHEN a registration request is submitted, THE Auth_Service SHALL hash the password using bcrypt with a minimum work factor of 12 before storing it.
5. WHEN a login request is submitted with a valid email and matching password, THE Auth_Service SHALL issue a signed session token with a 24-hour lifetime to the User.
6. WHEN a login request is submitted with a valid email and a non-matching password, THE Auth_Service SHALL return an authentication failure error without revealing which credential is incorrect.
7. WHEN a login request is submitted with an email address not associated with any User, THE Auth_Service SHALL return an authentication failure error without revealing that the email does not exist.
8. IF a session token has expired or is otherwise invalid, THEN THE Auth_Service SHALL reject the request with an HTTP 401 response without executing any business logic.
9. WHEN a login endpoint receives 5 consecutive failed attempts from the same IP address within a 10-minute window, THE Auth_Service SHALL block further login attempts from that IP for 15 minutes and return an error indicating the account is temporarily locked.

### Requirement 2: Google OAuth Authentication

**User Story:** As a User, I want to sign in with my Google account, so that I can access the application without managing a separate password.

#### Acceptance Criteria

1. THE Auth_Service SHALL support Google OAuth 2.0 as an authentication provider.
2. WHEN a User initiates Google OAuth sign-in and grants consent, THE Auth_Service SHALL create a new User account if no account exists for the returned Google email address, and redirect the User to the application home page within 3 seconds.
3. WHEN a User initiates Google OAuth sign-in and an account already exists for the returned Google email address, THE Auth_Service SHALL authenticate the User against the existing account and redirect the User to the application home page within 3 seconds.
4. WHEN a User denies Google OAuth consent, THE Auth_Service SHALL redirect the User to the login page with an error message indicating that consent is required to sign in.
5. IF the Google OAuth provider returns an error response, THEN THE Auth_Service SHALL log the error and display an error message to the User indicating that sign-in failed and they should try again.
6. IF the Google OAuth provider is unreachable for more than 10 seconds, THEN THE Auth_Service SHALL display an error message to the User indicating that the authentication service is unavailable and preserve the User's current session state.

### Requirement 3: User Profile Management

**User Story:** As a registered User, I want to view and update my profile information, so that collaborators can identify me within shared trips.

#### Acceptance Criteria

1. THE Profile_Service SHALL store a display name, avatar URL, and email address for each User.
2. WHEN a User requests their own profile, THE Profile_Service SHALL return the current display name, avatar URL, and email address for that User.
3. WHEN a User submits a profile update with a display name between 1 and 64 characters, THE Profile_Service SHALL persist the updated display name and return the updated profile.
4. IF a User submits a profile update with a display name that is empty (0 characters) or exceeds 64 characters, THEN THE Profile_Service SHALL return a validation error indicating the rejected constraint without persisting any changes.
5. WHEN a User uploads an avatar image of type JPEG, PNG, or WebP with a size between 1 byte and 5 MB, THE Profile_Service SHALL persist the new avatar and return the updated avatar URL.
6. IF a User uploads an avatar file exceeding 5 MB or of an unsupported format, THEN THE Profile_Service SHALL return a validation error indicating the rejected constraint without modifying the existing avatar URL.

### Requirement 4: Trip Creation

**User Story:** As a User, I want to create a new trip with a destination, date range, and type, so that I can begin planning my travel.

#### Acceptance Criteria

1. WHEN a User submits a trip creation request, THE Trip_Service SHALL create a new Trip with the provided destination city, start date, end date, and trip type, and return the created Trip including its system-assigned unique identifier.
2. WHEN a Trip is created, THE Trip_Service SHALL automatically assign the creating User as a TripMember with the ``Owner`` role.
3. IF a trip creation request is submitted with a start date that is later than the end date, THEN THE Trip_Service SHALL reject the request and return a validation error indicating the date range is invalid, without creating a Trip.
4. IF a trip creation request is submitted with an empty destination city, THEN THE Trip_Service SHALL reject the request and return a validation error indicating the destination is required, without creating a Trip.
5. IF a trip creation request is submitted with a trip type other than ``Solo`` or ``Group``, THEN THE Trip_Service SHALL reject the request and return a validation error indicating the accepted values, without creating a Trip.
6. THE Trip_Service SHALL support trip durations from 1 day to 365 days inclusive, where duration is calculated as (end date − start date + 1) in calendar days.
7. IF a trip creation request is submitted with a destination city name exceeding 100 characters, THEN THE Trip_Service SHALL reject the request and return a validation error indicating the maximum length, without creating a Trip.
8. IF a trip creation request is submitted with a start date that is in the past relative to the current calendar date, THEN THE Trip_Service SHALL reject the request and return a validation error indicating the start date must be today or a future date, without creating a Trip.

### Requirement 5: Trip Editing and Deletion

**User Story:** As a Trip Owner or Editor, I want to update or remove a trip, so that I can keep trip details accurate or discard cancelled plans.

#### Acceptance Criteria

1. WHEN a TripMember with the ``Owner`` or ``Editor`` role submits a trip update request with at least one valid field (destination city, start date, end date, or trip type), THE Trip_Service SHALL persist only the provided fields and return the full updated Trip.
2. WHEN a TripMember with the ``Viewer`` role submits a trip update request, THE Trip_Service SHALL return a permission error without modifying the Trip.
3. WHEN a TripMember with the ``Owner`` role submits a trip deletion request, THE Trip_Service SHALL delete the Trip along with all associated TripMembers, ItineraryItems, Expenses, and ExpenseSplits, and return a confirmation response.
4. WHEN a TripMember with the ``Editor`` or ``Viewer`` role submits a trip deletion request, THE Trip_Service SHALL return a permission error without deleting the Trip.
5. IF a trip update request changes the start date or end date such that existing ItineraryItems fall outside the new date range, THEN THE Trip_Service SHALL return a validation error listing the IDs of the affected ItineraryItems without persisting the date change.
6. IF a trip update request is submitted with no fields provided or all fields empty, THEN THE Trip_Service SHALL return a validation error indicating at least one field must be provided.
7. WHEN a trip update request changes the start date or end date to a range that is invalid (start later than end or duration exceeding 365 days), THE Trip_Service SHALL return a validation error without persisting the date change.

### Requirement 6: Collaborator Invitation

**User Story:** As a Trip Owner or Editor, I want to invite other Users to my trip via a unique link or email, so that we can plan the trip together.

#### Acceptance Criteria

1. WHEN a TripMember with the ``Owner`` or ``Editor`` role requests an invitation, THE Collaboration_Service SHALL generate a unique Invitation_Link for the Trip that is valid for exactly 7 days from the moment of generation.
2. WHEN a TripMember with the ``Owner`` or ``Editor`` role sends an invitation, THE Collaboration_Service SHALL accept a target email address of at most 254 characters and an intended Role of ``Editor`` or ``Viewer``.
3. IF the target email address provided at invitation time does not conform to standard email format, THEN THE Collaboration_Service SHALL return a validation error and SHALL NOT generate an Invitation_Link.
4. WHEN a User follows a valid Invitation_Link and is authenticated, THE Collaboration_Service SHALL add the User as a TripMember with the Role specified at invitation time within 3 seconds.
5. WHEN a User follows an Invitation_Link that has already been used to join the Trip, THE Collaboration_Service SHALL return an informative message without creating a duplicate TripMember record.
6. IF an Invitation_Link has expired after 7 days from generation, THEN THE Collaboration_Service SHALL return an expiry error and SHALL NOT add the User as a TripMember.
7. WHEN a TripMember with the ``Owner`` role changes another TripMember's Role, THE Collaboration_Service SHALL persist the updated Role and the change SHALL be reflected within 3 seconds for all active sessions on that Trip.
8. IF a TripMember without the ``Owner`` role attempts to change another TripMember's Role, THEN THE Collaboration_Service SHALL return a permission error without modifying the existing Role.
9. THE Collaboration_Service SHALL enforce that each Trip has exactly one TripMember with the ``Owner`` role at all times, rejecting any Role change that would result in zero or more than one ``Owner``.

### Requirement 7: Trip Dashboard

**User Story:** As a TripMember, I want to see a synchronized dashboard for my trip, so that I can view the latest itinerary and budget information alongside other collaborators.

#### Acceptance Criteria

1. WHEN a TripMember opens the Dashboard for a Trip, THE Dashboard SHALL display the trip name, destination city, start date, end date, trip type, and the list of TripMembers with their Roles.
2. WHEN a TripMember with the ``Editor`` role updates the Itinerary, THE Dashboard SHALL reflect the updated Itinerary for all TripMembers currently viewing the Dashboard within 5 seconds without requiring a full page reload.
3. WHILE a TripMember is viewing the Dashboard, THE Dashboard SHALL display the current total spent in IDR and the remaining budget in IDR, where remaining budget is calculated as the total trip budget minus the current total spent.
4. WHEN a TripMember with the ``Viewer`` role views the Dashboard, THE Dashboard SHALL display all content in read-only mode, disabling all edit controls.
5. IF the Dashboard fails to load trip data within 10 seconds of being opened, THEN THE Dashboard SHALL display an error message indicating the data could not be retrieved and provide a retry option.
6. IF the real-time synchronization connection is interrupted while a TripMember is viewing the Dashboard, THEN THE Dashboard SHALL display a status indicator informing the TripMember that live updates are unavailable until the connection is restored.

### Requirement 8: Itinerary Item Management

**User Story:** As a TripMember with editing access, I want to add, edit, and delete activities on specific days of my itinerary, so that I can build a detailed day-by-day plan.

#### Acceptance Criteria

1. WHEN a TripMember with the ``Owner`` or ``Editor`` role submits an itinerary item creation request, THE Itinerary_Service SHALL create an ItineraryItem associated with the specified Trip day, containing place name (maximum 100 characters), address (maximum 255 characters), category, notes (maximum 1000 characters), estimated duration in minutes, and an optional Google Maps location link.
2. WHEN an ItineraryItem creation request is submitted with an estimated duration of less than 1 minute or greater than 1440 minutes, THE Itinerary_Service SHALL return a validation error.
3. WHEN an ItineraryItem creation request is submitted for a date that falls outside the Trip's start date and end date range, THE Itinerary_Service SHALL return a validation error.
4. WHEN a TripMember with the ``Owner`` or ``Editor`` role submits an itinerary item update, THE Itinerary_Service SHALL persist the updated fields (place name, address, category, notes, estimated duration, and Google Maps location link) and return the updated ItineraryItem.
5. WHEN a TripMember with the ``Owner`` or ``Editor`` role submits an itinerary item deletion request for an existing ItineraryItem, THE Itinerary_Service SHALL remove the ItineraryItem and return the updated ordered list of remaining ItineraryItems for that day.
6. WHEN a TripMember with the ``Viewer`` role attempts to create, update, or delete an ItineraryItem, THE Itinerary_Service SHALL return a permission error.
7. THE Itinerary_Service SHALL accept the following category values for an ItineraryItem: ``Accommodation``, ``Transportation``, ``Food & Beverage``, ``Attraction``, ``Shopping``, ``Others``.
8. IF an update or delete request references an ItineraryItem ID that does not exist within the Trip, THEN THE Itinerary_Service SHALL return a not-found error without modifying any other ItineraryItems.
9. IF an itinerary item creation or update request is submitted with a place name, address, or notes exceeding their respective maximum lengths, THEN THE Itinerary_Service SHALL return a validation error identifying each field that exceeds its limit.

### Requirement 9: Drag-and-Drop Itinerary Reordering

**User Story:** As a TripMember with editing access, I want to reorder activities within a day using drag-and-drop, so that I can adjust the schedule without manually re-entering items.

#### Acceptance Criteria

1. WHEN a TripMember with the ``Owner`` or ``Editor`` role drags an ItineraryItem to a new position within the same day, THE Itinerary_Service SHALL persist the updated ordering for all ItineraryItems in that day.
2. WHEN an ItineraryItem is reordered, THE Itinerary_Service SHALL assign a unique, monotonically increasing sort index to each ItineraryItem within the day such that the resulting order matches the User's intended drop position.
3. WHEN an ItineraryItem reorder request is received, THE Itinerary_Service SHALL complete the persistence operation within 500 ms under a load of up to 50 concurrent reorder requests.
4. THE Itinerary_Service SHALL preserve the relative ordering of all ItineraryItems not involved in the drag operation after a reorder.
5. IF a TripMember without the ``Owner`` or ``Editor`` role attempts to reorder an ItineraryItem, THEN THE Itinerary_Service SHALL reject the request and return an error indicating insufficient permissions without modifying any ItineraryItem ordering.
6. IF two or more TripMembers submit reorder operations for the same day concurrently, THEN THE Itinerary_Service SHALL serialize the operations such that each operation is applied to the result of the previous one, and SHALL notify each submitting TripMember of the final ordering.

**Correctness Properties (Property-Based Testing):**

- **Permutation invariant**: After any reorder operation on a day's items, the set of ItineraryItem IDs for that day SHALL be identical to the set before the reorder (no items are created or lost).
- **Total order invariant**: After any reorder, the sort indices for all ItineraryItems within a day SHALL form a strictly increasing sequence with no duplicates.
- **Idempotence**: Applying the same reorder operation twice SHALL produce the same ordering as applying it once.

### Requirement 10: Trip Budget Setup

**User Story:** As a TripMember with editing access, I want to set a target total budget for the trip in IDR, so that I can track spending against a defined limit.

#### Acceptance Criteria

1. WHEN a TripMember with the ``Owner`` or ``Editor`` role submits a budget setup request with a valid amount, THE Budget_Service SHALL persist the target total budget amount in IDR for the Trip, overwriting any previously set target budget.
2. IF a budget setup request is submitted with an amount less than or equal to 0 IDR, THEN THE Budget_Service SHALL return a validation error indicating the amount is invalid and SHALL NOT persist any budget value.
3. IF a budget setup request is submitted with an amount exceeding 999,999,999,999 IDR, THEN THE Budget_Service SHALL return a validation error indicating the amount exceeds the maximum allowed and SHALL NOT persist any budget value.
4. WHEN the target budget is updated, THE Budget_Service SHALL recalculate and return the updated remaining budget, defined as the target budget minus the sum of all logged Expense amounts for the Trip, where a negative value indicates the Trip is over budget.
5. IF a TripMember without the ``Owner`` or ``Editor`` role submits a budget setup request, THEN THE Budget_Service SHALL return an authorization error indicating insufficient permissions and SHALL NOT persist any budget value.

### Requirement 11: Expense Logging

**User Story:** As a TripMember, I want to log individual expenses by category, so that I can track where trip money is being spent.

#### Acceptance Criteria

1. WHEN a TripMember submits an expense log request, THE Budget_Service SHALL create an Expense record containing the amount in IDR (between 1 and 999,999,999,999 IDR), category (one of the accepted category values), description (maximum 255 characters), payer (a TripMember of the associated Trip), and the date of the expense.
2. IF an expense log request is submitted with an amount less than 1 IDR or greater than 999,999,999,999 IDR, THEN THE Budget_Service SHALL reject the request and return a validation error indicating the amount is out of the valid range.
3. THE Budget_Service SHALL accept the following category values for an Expense: ``Accommodation``, ``Transportation``, ``Food & Beverage``, ``Tickets/Attractions``, ``Shopping``, ``Others``.
4. IF an expense log request is submitted with a category value not in the accepted category list, THEN THE Budget_Service SHALL reject the request and return a validation error indicating an invalid category.
5. WHEN an expense is successfully created, THE Budget_Service SHALL update the total spent amount for the Trip to equal the sum of all Expense amounts for that Trip.
6. IF an expense log request references a payer who is not a TripMember of the associated Trip, THEN THE Budget_Service SHALL reject the request and return a validation error indicating the payer is not a member of the Trip.
7. WHEN a TripMember with the ``Owner`` or ``Editor`` role submits a delete request for an Expense, THE Budget_Service SHALL remove the Expense record and recalculate the total spent amount for the Trip as the sum of all remaining Expense amounts for that Trip.
8. IF a TripMember with the ``Viewer`` role submits a delete request for an Expense, THEN THE Budget_Service SHALL reject the request and return an authorization error indicating insufficient permissions.

### Requirement 12: Group Expense Split and Settlement Calculation

**User Story:** As a Trip Owner or Editor, I want to log who paid an expense and split it among selected members, so that the system can calculate who owes whom for final settlement.

#### Acceptance Criteria

1. WHEN a group expense is logged, THE Budget_Service SHALL accept a payer (one TripMember) and a list of between 2 and 50 TripMembers who share the expense.
2. WHEN a group expense is logged with an equal-split instruction, THE Budget_Service SHALL divide the Expense amount evenly among all selected sharing TripMembers, rounding each share down to the nearest IDR unit and assigning any remainder to the first TripMember in the sharing list.
3. WHEN a group expense is logged with a custom-split instruction, THE Budget_Service SHALL accept an explicit IDR amount per sharing TripMember and SHALL return a validation error indicating the mismatch if the sum of all custom share amounts does not equal the total Expense amount.
4. WHEN settlements are requested for a Trip, THE Budget_Service SHALL compute the minimum number of net transfer Settlements such that all inter-member balances are resolved, completing the computation within 5 seconds for up to 50 members and 1,000 expenses.
5. WHEN settlements are computed, THE Budget_Service SHALL return each Settlement as a tuple of (debtor TripMember, creditor TripMember, amount in IDR) where the amount is a positive integer greater than 0 IDR.
6. WHEN settlements are computed and all TripMembers have a net balance of 0 IDR, THE Budget_Service SHALL return an empty settlement list.
7. IF an expense split request names a TripMember who is not a member of the associated Trip, THEN THE Budget_Service SHALL return a validation error without persisting any split records.
8. IF an expense split request contains a sharing list with fewer than 2 or more than 50 TripMembers, THEN THE Budget_Service SHALL return a validation error indicating the sharing list size is invalid without persisting any split records.
9. IF an expense split request references a payer who is not a TripMember of the associated Trip, THEN THE Budget_Service SHALL return a validation error without persisting any split records.

**Correctness Properties (Property-Based Testing):**

- **Zero-sum invariant**: For any set of Expenses with splits, the sum of all net balances across all TripMembers SHALL equal 0 IDR. Formally: ``Σ balance(member) = 0`` for all members.
- **Settlement completeness**: After applying all computed Settlements, every TripMember's net balance SHALL equal 0 IDR.
- **Settlement minimality (metamorphic)**: The number of Settlements returned SHALL be less than or equal to ``N - 1`` where N is the number of TripMembers with a non-zero balance.
- **Equal-split round-trip invariant**: For any Expense of amount A split equally among N members, the sum of all computed shares SHALL equal A exactly (the remainder distribution is lossless).
- **Custom-split round-trip invariant**: For any custom-split Expense, the sum of all custom share amounts SHALL equal the total Expense amount A exactly.
- **Idempotence of settlement computation**: Computing settlements twice on the same set of Expenses SHALL produce an equivalent set of Settlements (same debtors, creditors, and amounts, possibly in different order).
- **Error condition — overpayment split**: Submitting a custom split where the sum of shares exceeds the total Expense amount SHALL always produce a validation error, never a persisted record.
- **Error condition — underpayment split**: Submitting a custom split where the sum of shares is less than the total Expense amount SHALL always produce a validation error, never a persisted record.

### Requirement 13: Budget Analytics

**User Story:** As a TripMember, I want to see a visual summary comparing planned versus actual spending by category, so that I can understand where the budget is being used.

#### Acceptance Criteria

1. WHEN a TripMember views the budget analytics section, THE Budget_Service SHALL provide a per-category breakdown containing the planned budget amount in IDR and the total actual spending in IDR for each Expense category.
2. THE Budget_Service SHALL compute the per-category planned amount as the proportion of the total target budget allocated to each category, rounded down to the nearest whole IDR, defaulting to 0 IDR for categories with no explicit allocation.
3. WHEN a TripMember views the budget analytics section, THE Budget_Service SHALL provide a total-level comparison: target budget in IDR, total spent in IDR, and remaining budget in IDR, where remaining budget equals target budget minus total spent.
4. WHEN an Expense is created, updated, or deleted, THE Budget_Service SHALL update the analytics data within 2 seconds of the operation completing.

### Requirement 14: Place Recommendation and Discovery

**User Story:** As a User, I want to search and browse curated popular destinations and spots in Indonesia, so that I can discover places to add to my itinerary.

#### Acceptance Criteria

1. THE Recommendation_Service SHALL maintain a curated dataset of Places in Indonesia, each containing a name (1–100 characters), city (1–100 characters), province, category (one of: ``Nature``, ``Culture``, ``Culinary``, ``Adventure``, ``Accommodation``, ``Entertainment``), description (1–500 characters), and an optional image URL (valid URL format, maximum 2048 characters).
2. WHEN a User submits a search query of between 2 and 100 characters, THE Recommendation_Service SHALL return a list of up to 50 Places whose name or city contains the query string (case-insensitive), sorted by name ascending.
3. WHEN a User submits a search query of fewer than 2 characters, THE Recommendation_Service SHALL return a validation error without executing a search.
4. IF a User submits a search query exceeding 100 characters, THEN THE Recommendation_Service SHALL return a validation error without executing a search.
5. WHEN a User browses recommendations by category, THE Recommendation_Service SHALL return up to 50 Places matching the specified category, sorted by name ascending.
6. IF a User browses recommendations with a category value not in the accepted category list, THEN THE Recommendation_Service SHALL return a validation error without executing a search.
7. WHEN a User selects "Add to Itinerary" on a Place recommendation card, THE Itinerary_Service SHALL pre-populate an ItineraryItem creation form with the Place's name, address, and category.
8. IF the Places data source is unavailable, THEN THE Recommendation_Service SHALL return a service unavailability error and SHALL NOT return partial or corrupted data.
9. THE Recommendation_Service SHALL return search and browse results within 1 second for queries against a dataset of up to 10,000 Place records.

**Correctness Properties (Property-Based Testing):**

- **Search subset invariant**: For any search query Q, every Place returned SHALL contain Q in its name or city field (case-insensitive). No Place in the result set SHALL lack Q in both fields.
- **Category filter invariant**: For any category filter C, every Place returned SHALL have a category equal to C. No Place with a different category SHALL appear in the result.
- **Monotonicity (metamorphic)**: For any search query Q that is a prefix of query Q', the result set of Q SHALL be a superset of the result set of Q' (longer queries produce equal or fewer results).

### Requirement 15: Data Integrity and Schema Constraints

**User Story:** As the system operator, I want the database to enforce referential integrity and constraints, so that corrupt or orphaned records cannot exist.

#### Acceptance Criteria

1. THE System SHALL enforce a foreign key constraint from TripMember to Trip, cascading deletes from Trip to TripMember, and a foreign key constraint from TripMember to User, restricting deletion of a User record while any TripMember record references that User.
2. THE System SHALL enforce a foreign key constraint from ItineraryItem to Trip, cascading deletes from Trip to ItineraryItem.
3. THE System SHALL enforce a foreign key constraint from Expense to Trip and from Expense to the payer TripMember, cascading deletes from Trip to Expense.
4. THE System SHALL enforce a foreign key constraint from ExpenseSplit to Expense and from ExpenseSplit to TripMember, cascading deletes from Expense to ExpenseSplit.
5. THE System SHALL enforce a unique constraint on the combination of (Trip ID, User ID) in the TripMember table, preventing duplicate membership records.
6. THE System SHALL store all monetary amounts as 64-bit signed integer values representing whole IDR units in the range 1 to 999,999,999,999 inclusive, rejecting any attempt to store a value outside this range.
7. THE System SHALL enforce a unique constraint on the combination of (Expense ID, TripMember ID) in the ExpenseSplit table, preventing duplicate split records for the same Expense and TripMember.

**Correctness Properties (Property-Based Testing):**

- **Monetary integer invariant**: For any arithmetic operation on Expense amounts (sum, subtraction for settlement), the result SHALL be representable as a 64-bit signed integer without overflow for trip budgets up to 999,999,999,999 IDR and up to 1,000 Expenses per trip.

### Requirement 16: API Authorization

**User Story:** As a system operator, I want all API routes to enforce authentication and role-based authorization, so that Users cannot access or modify trips they are not permitted to.

#### Acceptance Criteria

1. WHEN any API request is received with a missing, expired, or otherwise invalid session token, THE System SHALL return an HTTP 401 Unauthorized response without executing any business logic.
2. WHEN a TripMember with the ``Viewer`` role submits a mutating request (create, update, or delete) to any Trip, Itinerary, or Budget endpoint, THE System SHALL return an HTTP 403 Forbidden response.
3. WHEN an authenticated User who is not a TripMember of a given Trip submits any request to that Trip's endpoints, THE System SHALL return an HTTP 404 Not Found response to avoid disclosing the existence of the Trip.
4. WHEN a TripMember with the ``Editor`` role attempts to delete a Trip, THE System SHALL return an HTTP 403 Forbidden response.
5. WHEN a TripMember with the ``Owner`` role submits any request to a Trip they own, THE System SHALL permit the request to proceed, subject to input validation.
6. WHEN an API request passes authentication and authorization checks and contains input that fails schema validation, THE System SHALL return an HTTP 422 Unprocessable Entity response that identifies each invalid field by name and describes the validation rule it violated.

### Requirement 17: Tech Stack Constraints

**User Story:** As a developer, I want the system to be built on the specified technology stack, so that the codebase is consistent and maintainable.

#### Acceptance Criteria

1. THE System SHALL be implemented using Next.js with the App Router and TypeScript.
2. THE System SHALL use Tailwind CSS, Shadcn UI, and Lucide Icons for all UI components.
3. THE System SHALL use PostgreSQL as the primary database and Prisma ORM for all database access.
4. THE System SHALL use TanStack Query (React Query) or Next.js Server Actions for data fetching and mutations on the client.
5. THE System SHALL implement Drag-and-Drop functionality using ``@hello-pangea/dnd`` or ``dnd-kit``.
6. THE System SHALL define the Prisma schema with models for: User, Trip, TripMember, ItineraryItem, Expense, and ExpenseSplit.
7. THE System SHALL expose TypeScript utility functions for expense splitting and settlement calculation that are pure functions with no side effects, accepting numeric inputs in the range 1 to 999,999,999,999 IDR, enabling deterministic property-based testing.
